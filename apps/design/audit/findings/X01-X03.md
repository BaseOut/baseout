## 1 Job

- **X01.** The user is scanning a list to *find one row* and to *compare rows on one attribute*.
  `storybook.ts:1513` (`table`) states it: "The workhorse for run history and audit data." The lens'
  job is therefore: does the column header, everywhere, say the same three things — what this column
  is, that it can be sorted, and which way it is sorted now.
- **X02.** Narrow a list you cannot read whole. `storybook.ts:3009` (`pattern-table-toolbar`):
  "Search, filters and a pager wrapped around a data table."
- **X03.** Reach row 200 of 1,240 without the page rendering 1,240 rows.
  `storybook.ts:3067` (`pattern-node-showmore`) carves out the hierarchy case.

All three jobs are **STATED**, in the catalog, in unusual detail. That matters for the ranking below:
none of these findings is a missing decision. Every one of them is a written rule with partial reach.

## 2 First five seconds

The lens-level equivalent: *does a user who has learned one list know how to read the next one?*

- **X03: yes.** Every paged surface ends in the identical row — `Rows [20]` · `1–20 of 57` ·

## 3 Navigation and orientation

Sort and page state are **ephemeral by design and by contract**: `pattern-table-toolbar` says "`page`
is ephemeral (a reload starts at page 1)" and `wireTableSort` holds `col`/`dir` in a closure
(`tableSort.ts:30-31`). So no list's sort or page survives a refresh or is shareable by URL.

This is a **deliberate, written** choice, not drift, and it is consistent everywhere — so it is not a
consistency finding. It is a *contract* finding against D07 ("addressable state"), which ruled that a
run has one address. A user who sorts Backups by Status to show a colleague cannot send that view.
Filed once, at S3, as **F13**; it is one decision, not thirteen rows.

`pageSize` **does** persist (a stored user preference, `pattern-table-toolbar`), so the pager
deliberately persists the preference and deliberately drops the position. That asymmetry is correct
and should stay.

## 7 Cross-surface consistency

**The reference for each lens, and the measurement that makes it the reference.**

### X01 → `.tbl-colhead` + `wireTableSort` + the CSS caret, **plus DataMedia's `<button>` wrapper**

- **Adoption:** `.tbl-colhead` is in **17 of 23** header-declaring files; `wireTableSort` in **14**.
  Every rival construction has 1–2 files. The reference is the only one with more adopters than all
  eight rivals combined.
- **The measurement that decides it, and it is not the count.** `.tbl-colhead` is the only recipe
  that carries `global.css:1864` — `.tbl-colhead th :is(button, a, span) { font: inherit; letter-spacing:
  inherit; text-transform: inherit; color: inherit; }`. The comment above it records why: the UA
  stylesheet resets a form control's font, "so the rule above stopped at the cell and the sortable
  columns rendered in sentence case beside uppercase static ones (measured on the Attachments table,
  2026-07-31)." **A sortable header must contain a `<button>` to be keyboard-operable, and every
  rival recipe breaks visually the moment you add one.** That is what makes this recipe the reference
  rather than the popular one: it is the only one that survives being made accessible.
- **The one amendment the reference needs.** `wireTableSort` delegates from a click on a bare `<th>`
  (`tableSort.ts:54-55`), which no keyboard can reach. `DataMedia.astro:411-413,431-433` is the only
  table in the app whose headers are real `<button>`s. Converge on `.tbl-colhead` + `wireTableSort`
  **with DataMedia's button anatomy folded into it**, and delete DataMedia's private `data-md-sort`
  sorter in the same move. This is not a compromise between two patterns; it is the one pattern that
  each half of the app already has, assembled once.
- **`aria-sort` is the missing third piece** and belongs on the same element, so it is one change.

### X02 → `.sch-tb` + `FacetFilter` + `mountRefineCollapse` + `collapsingSearch`, stamped by `toolbarFit`

- **Adoption:** `FacetFilter` 13 · `refineCollapse` 10 · `.sch-tb` 9 surfaces. The three
  non-`.sch-tb` toolbars have **1 file each and identical CSS**, so there is nothing to weigh
  against: they are copies, not alternatives.
- **The measurement that decides it.** `.sch-tb` is the only toolbar family with a **width answer**.
  `toolbarFit.ts:18,37-40` measures `#layout-content`'s `clientWidth`, not the viewport, and stamps
  `data-narrow` below 1440 — which `global.css:2244` (drop the button word) and `:2277-2287`
  (collapse the search to a 32px magnifier) consume. The three copies have `flex-wrap: wrap` and
  nothing else, so their only answer to running out of room is to become two rows. The header comment
  at `toolbarFit.ts:4-16` records the measurement that produced the number: "at a 1440 laptop with
  split on, the content column is ~795px while the media query still reads 1440… the Data toolbar
  went from one row to four while the media tier reported the identical `1024-1600 laptop`."
  **A media query cannot see split view; only `.sch-tb` asks the right question.**

### X03 → `TablePager.astro` + `createPager` (flat) and `pattern-node-showmore` (hierarchy)

- **Adoption: total.** One pager file, **13 mounts, zero look-alikes.** This lens is *already
  converged* — the only one of the three that is.
- **The measurement that decides it is a comparison, and it is the finding that ties X01–X03
  together.** Pagination was in exactly the same state as headers are now — `TablePager.astro:4-11`
  records it: "hand-copied into four surfaces before Schema needed it on five more; it is a component
  now… there is no second pager left to drift from." Same repo, same period, same authors.
  **Pagination converged because someone made a component. Headers did not because the catalog
  shipped a CSS class and a JS function instead** — `apps/web/src/components/ui/` contains
  `TablePager.astro` and **no** `Table.astro` / `TableHead.astro`. That is the single cause the
  worklist asked for, and it is falsifiable: the lens with a component has 1 implementation, the lens
  with a class has 9.

### The rule check X03 asked for: does `decision-tree-showmore-not-pager` hold?

**It holds, in both directions, and two surfaces defend it in writing.**

- Applied where it should be: `SchemaBrowse.astro:290,823-964` (base ▸ table ▸ field) ·
  `BaseSelectionTable.astro:1011` (workspace shell) · `recordReadBody.ts:81` (linked records).
- **Correctly refused where it should not be** — and both refusals are argued, not accidental:
  `DataComments.astro:1019` ("`decision-tree-showmore-not-pager` does not apply — it bans paging a
  [hierarchy]") and `DataMedia.astro:1549` ("the tree rule this replaces is about HIERARCHIES, where
  [a page boundary orphans a child]"). The catalog carries the same carve-out at
  `storybook.ts:3067` usageDo: a one-level grouping is not a tree, "because each group's header is
  re-drawn on every page it appears on."
- **No pager inside a tree anywhere in the census.** Schema Browse pages its Flat mode only.

This is the healthiest rule in the three lenses and I would change nothing about it.

## 9 Foreign or surprising

1. **Two surfaces sort from a toolbar menu instead of a column header.** `SchemaHealth.astro:212`
   and `SchemaDocs.astro:114` both render a `btn-square btn-ghost` with `lucide--arrow-up-down` and
   a tooltip ("Sort bases" / "Sort documents"). Every other list in the app sorts by clicking a
   header. A user who has learned Backups will click Health's column label and nothing will happen.
   **The cause is structural, and it is the deeper half of X01's story:** Health's "table" is a CSS
   grid of `<div>`s (`.hl-metrics-head`, `SchemaHealth.astro:295,730`) and Interfaces' is a flex row
   of `<span>`s (`.if-thead`, `SchemaInterfaces.astro:357-358`). Neither can take a `<th>`, so
   neither can take the `[data-sort-col]` caret — the shared mechanism is **selector-bound to a
   table element**. Three of the app's "tables" are not tables, and that, not carelessness, is why
   they grew their own heads. → F5.
2. **`SchemaHealth.astro:295` puts `aria-hidden="true"` on its column-label band** — which is
   verbatim the thing the catalog's own `table` usageDont forbids: "Don't render a static
   `aria-hidden` head over a scrolling list of hundreds and call it a header — it cannot be sorted,
   and a screen reader is told to ignore the only column labels on screen." Schema is a **reference
   surface**, so per the charter this is S2 against the reference, not immunity. → F6.
3. **Home's tables are the catalog's example, verbatim.** `SpaceHomeView.astro:269` is
   `<tr class="text-xs uppercase tracking-wider text-base-content/60">` — which is character-for-character
   the head row in the `table` entry's own example (`storybook.ts:1550`), repeated in
   `pattern-audit-table` (`:2597`) and `pattern-table-toolbar` (`:3055`). Home did not invent a
   ninth recipe; **it copied the catalog.** → F2, and it is the second cause.

## 10 Density and rhythm

- The 11px/700/.04em band is the right register for utility-admin density and is in 17 files.
  The drift is toward **lighter and larger** (600 weight, 12px, `/.45`), which reads as a marketing
  table, not a Linear one. `NEEDS-MEASUREMENT` for the paint, but the declarations are unambiguous.
- Spacing is on the grid throughout: `.tpg` gap 16 / margin-top 12 / padding-top 12
  (`TablePager.astro:52`); `.au-tbl thead th` padding `.5rem .75rem` = 8/12px; the three copied
  toolbars gap 8, margin-bottom 1rem = 16px. **No 4px-grid violation found in these three lenses.**
- One sub-floor size: `.br-sortind` at 8px (`SchemaBrowse.astro:695`), correctly `ds-ok`'d as a
  glyph rather than text. Legitimate.

## What is good here — do not touch

1. **`TablePager` is the model this whole audit is arguing for, and it is finished.** One file, 13
   mounts, zero look-alikes, `tpg-tight` handled as a modifier rather than a second copy
   (`TablePager.astro:56-59`), page-size persisted as a user preference and page position
   deliberately not. It is also the *proof* for F2: the same team solved the same problem the moment
   the pattern became a component. Do not "improve" it; point at it.
2. **`decision-tree-showmore-not-pager` holds in both directions and is defended in prose at the two
   places most likely to break it.** `DataComments.astro:1019` and `DataMedia.astro:1549` each argue
   *why the rule does not apply to them* before choosing the pager. That is a rule that has been
   thought about rather than obeyed, and the reasoning is worth more than the rule.
3. **`FacetFilter` — 13 importers, zero hand-rolled facet dropdowns remaining.** X02's filtering half
   is converged. Whatever happens to the toolbar containers, do not reopen the facet.
4. **`global.css:1859-1868`.** The `:is(button, a, span)` re-inheritance, with the measurement that
   caused it written above it. It is small, it looks like boilerplate, and deleting it would silently
   return every sortable header to sentence case. It is also the precondition for fixing F3 — it must
   survive any header refactor.
5. **`toolbarFit.ts`'s reasoning, in full.** Two header comments record (a) why the threshold moved
   from the viewport to the content column — split view — and (b) why it measures the *section*
   rather than each toolbar, with Oleh's rule quoted: "якщо тут коротка кнопка з іконкою, значить
   всюди". Both are corrections of a shipped bug, both are non-obvious, and a future refactor that
   re-derives from the viewport would reintroduce both. Extend this file; do not rewrite it.
6. **`pattern-node-showmore`'s "say what is left" rule** (`Show 25 more of 340`) and the reset-to-
   first-chunk-on-filter-change contract. It is the right copy and the right behaviour; F11 is asking
   the other three call sites to adopt it, not asking this to change.
7. **The three distinct no-matches states** on Backups, Reports and Restore history
   (`:279`, `:222`, `:253`) — each separate from the never-run empty state, which is exactly what the
   toolbar entry asks for and is often the first thing dropped.
8. **The 4px grid holds across all three lenses.** Every pager, toolbar and header-cell metric
   measured here is a multiple of 4. Nothing to fix, and worth saying so.
