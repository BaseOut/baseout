## 1 Job

- **X10.** The user is deciding whether to let an irreversible thing happen, and afterwards needs to
  know it happened and whether they can take it back. `specs/00-design-principles.md` — "trust
  signals first (is it working / what's next / did the last run succeed)" — makes this a trust
  surface, not a politeness surface. `D06` states the rule; `pattern-undo-toast` states the division
  of labour ("Reserve dialogs for what cannot be undone").
- **X11.** The user is changing a stored thing and needs to know, at every moment, whether what is on
  screen is stored. **UNSTATED in `specs/`** — no spec doc names a save contract. `D30` is the only
  written rule and it governs one section. That absence is itself a finding (X11-F8).
- **X14.** The user pressed something and needs to know it is happening, is not lost, and must not be
  able to press it twice. **UNSTATED in `specs/`.**

## 2 First five seconds

The three lenses share one failure mode: **the app is at its quietest exactly where it is most
consequential.** Pressing `Delete` on an automation row produces no dialog, no toast, no motion other
than the row dimming to `opacity: .55`
(`SchemaAutomations.astro:364`) — the same visual weight as a filter change. Pressing `Save` on a
source produces no spinner and no confirmation of any kind (`SourceDetailView.astro:328-333`). Pressing
`Test connection` produces a full-sentence success line before the network could have answered
(`DestinationDetailView.astro:317-322`). A first-time reader learns that this product does not react to
being used, and then meets `Restore into Airtable?` — seven facts and two alerts
(`RestoreView.astro:481-508`) — which is correct, but arrives without a scale to read it against,
because nothing else in the app ever asks.

## 3 Navigation and orientation

Exit is where X11 fails hardest. **`grep -rn beforeunload apps/web/src` returns 0. `grep -rn popstate
apps/web/src` returns 0.** Exactly one exit is gated anywhere in the product: the wizard's
document-level anchor-click interceptor (`IntegrationsSetupWizard.astro:871-886`), which is a good
piece of work — it ignores modified clicks and new-tab clicks (`:874-876`), ignores in-wizard links
that are not tagged exits (`:881`), and rewrites the dialog's own confirm href so the guard cannot
trap you (`:867-869`). It catches sidebar links too, because it is bound to `document`.

Everywhere else, leaving discards. The sharpest case is `ReportDefinitionView`: the page *knows* it is
dirty (`:654-655` sets `dirty` and unhides `Unsaved changes`) and puts a plain
`<a href="/reports">Cancel</a>` (`:404`) immediately to the left of the Save button. A user who
mis-reads `Cancel` as "cancel my edits" — the meaning it carries in the panel and in both registry
pages — loses the whole definition, with the warning label still lit two inches away.

## 4 Primary action

Destructive confirms: the primary action is the *safe* one. `ConfirmModal` defaults `cancelLabel` to
`Cancel` and `confirmClass` to `btn-primary` (`ConfirmModal.astro:48-52`), and destructive callers pass
`CONFIRM_DESTRUCTIVE = 'btn-outline btn-error'` (`lib/ui.ts:15`) — the one outline use
`decision-button-system` still sanctions. Eight call sites follow it. One does not: the Docs delete
dialog uses solid `btn-error` (`SchemaDocs.astro:269`), which makes the destroying button the loudest
thing in the dialog.

Cancel labels are inconsistent in a way that is not accidental but is not coordinated either: `Keep
it` (Settings/Reports/registries), `Keep running` (backup run), `Keep editing` / `Stay in setup`
(wizard), bare `Cancel` (Restore, Docs). The first four are good — they name what staying preserves.
Restore, the single most consequential dialog in the product, is the one that says only `Cancel`.

## 7 Cross-surface consistency

**X10 — three ways to destroy.** (a) `ConfirmModal` + `CONFIRM_DESTRUCTIVE`, 8 sites. (b) a bespoke
dialog with solid `btn-error`, 1 site (`SchemaDocs.astro:263`). (c) nothing at all, 4 paths (2 rows,
2 panel footers). The reference is **`ConfirmModal` as called by `BackupRunDetailView.astro:501,510`
and `RestoreView.astro:481`** — measurement: those three are the only destructive dialogs in the tree
that state the consequence in a `role="alert"` soft alert *inside* the dialog body and name what
staying preserves in the cancel label; they are also the pair `D06` itself cites as the recipe. Every
other destructive path is measured against them.

**X11 — eight save contracts, four of them competing for one job.**

| # | contract | where | exit semantics |
|---|---|---|---|
| C1 | Read/Edit segments · footer Save+Cancel · **all three exits discard** | `entityPanelController.ts:157`, footer `schemaReadBody.ts:305-314` | segment · Cancel · Escape → one function |
| C2 | Read/Edit segments · footer Save+Cancel · **Read segment neither saves nor reverts** | `SourceDetailView.astro:307-341`; `DestinationDetailView.astro:290-310` | Cancel reverts (`:323`), Escape reverts (`:335`), segment does neither (`:319`) |
| C3 | Modal form · `Register …` submit · dismiss discards | `SchemaAutomations.astro:328`, `SchemaInterfaces.astro:327`, `RelationshipPanel.astro:97` | dismiss = discard, silent |
| C4 | Always-editable page form · dirty flag · `Cancel` is a link that navigates away | `ReportDefinitionView.astro:399-405`, handler `:697-702` | link navigates, discards, no guard |
| C5 | Instant apply · per-row `Saved` flag · no Save button | `SettingsView.astro:169,230` | nothing to exit |
| C6 | Commit-on-blur | `RecipientInput.astro:152`, `schemaAutomations.ts:300`, `BaseSelectionTable.astro:1367` | blur commits |
| C7 | **No save at all** | `SchemaDocs.astro:773-777` | every route in overwrites the editor |
| C8 | Staged wizard · `Save changes` in edit mode · link-click exit guard | `IntegrationsSetupWizard.astro:135,471-487,871-886` | the only guarded exit in the product |

C1, C2, C4 and C7 all do the same job — *edit an existing object's fields in place* — four different
ways, on four surfaces a single user visits in one session. C3, C5, C6 and C8 are different jobs and
are each internally consistent; they are not the problem.

**The reference to converge on: C1 — `pattern-panel-edit-mode` as implemented by
`entityPanelController.ts` (`exitEdit`, `:157`) with the footer from `schemaReadBody.ts:305-314`.**
Two measurements make it the reference and not merely the incumbent: (1) it is the only in-place
editor where all three exits route through one function, so "Cancel" cannot come to mean different
things at different times — the comment at `:156` states the contract and the code is one line long;
(2) it is the only one where the read slot and the pending value cannot disagree, because every read
render goes through `draftObj` (`:142`), which overlays the draft onto the record. C2 has no such
overlay: `paintValue` is called only from the Save handler (`SourceDetailView.astro:328-332`), so
after the Read segment the visible value and the input value are different strings with no marker.

**X14 — eight ways to say "working", plus one absence.** (1) `setButtonLoading` — disable +
`aria-busy` + injected spinner, `lib/ui.ts:47-59`, 14 files. (2) `Button.astro`'s `loading` prop
(`:61`) — the catalog's own affordance, **zero callers**. (3) an inline `loading-spinner` inside a
status badge — 8 places (`BackupsListView:232`, `BackupRunDetailView:250,448`, `BackupRunBaseView:146,282`,
`ReportDefinitionView:235`, `RestoreView:534`, `RestoreHistoryView:199`); this is a different job — *the
object* is working, not *your click* — and it is consistent, so it is fine. (4) `<progress>` —
`ProgressBar.astro`, `RestoreView:541`, `BaseSelectionTable:419`. (5) `LiveRefresh` — a freshness stamp
plus `location.reload()` (`:56`). (6) bespoke spinner blocks — `StaticImport.astro:55`,
`BaseSelectionTable.astro:581`. (7) an `sr-only` live region only — `ReportDefinitionView`'s `say()`.
(8) a static result line with no pending phase — `DestinationDetailView:317-322`,
`SourceDetailView:343-349`. (9) nothing at all — registry `Save`, Health `Save prompt`
(`SchemaHealth.astro:1042`), Restore confirm (`restore/controller.ts:484`), Docs.

**The reference to converge on: `setButtonLoading` (`apps/web/src/lib/ui.ts:47-59`).** Measurement:
it is the only idiom that does all three of (a) `btn.disabled = loading` — which makes a
double-submit *impossible* rather than merely unlikely, (b) `aria-busy`, (c) a spinner inside the
pressed control so the feedback is where the eye already is. Every other idiom does at most one of
the three, and idiom (7) does none of them for a sighted user. It also already has the most call
sites (14 files) — this is a convergence the app has half-finished, not a new pattern.

## 8 Copy and tone

Good: `Keep it` / `Keep running` / `Keep editing` name what staying preserves. The wizard's discard
alert (`IntegrationsSetupWizard.astro:483-486`) explains *why* there is nothing to come back to
rather than just warning. `Won't retry` on a permanently failed attachment
(`BackupRunDetailView.astro:530`) and `Nothing to retry` (`:546`) are exactly right.

Wrong: **`Retry` says the result will "appear in History" while sitting inside History.** The button
is rendered in the History table's `go` cell (`ReportDefinitionView.astro:268`); the toast it fires
says `Re-running the report for <period>. It will appear in History when it finishes.` (`:807-808`).
The row the user just pressed is already in History, three columns to the left of their cursor, and
its status badge is not updated. The user is told to go and wait somewhere they already are.

Also wrong: `Re-checked the connection — reachable, credentials still valid.`
(`DestinationDetailView.astro:320`) is a claim of fact with no mechanism behind it and no failure
branch, printed directly under `Status reflects the last successful check, not live.` (`:133`). The
page states a caveat and then, on one click, contradicts it.

## 9 Foreign or surprising

The single most surprising thing in these three lenses: **`Delete` on an automation or interface row
is invisible until hover.** `.row-actions` is `opacity: 0; pointer-events: none` at rest
(`styles/components/row-actions.css:33`), revealed on `:hover` **or `:focus-within`** (`:34-35`). The
row itself is `role="button" tabindex="0"` and Enter opens the detail panel
(`schemaAutomations.ts:265-271`). So a keyboard user tabs onto the row, presses Tab twice — Edit, then
Delete, both of which only became visible at that moment — and Enter destroys the record with no
dialog and no undo. Nowhere else in the app can a keyboard user destroy something without being
asked. `D06` built the machinery for five surfaces and these two were not on the list.

Second: `Cancel` means three different things on three pages a user visits in one errand — revert my
edits (registry, panel), leave this page and discard everything (report definition), and stop this
running backup (`BackupRunDetailView.astro:510`).

## 10 Density and rhythm

`ConfirmModal` renders at `size="sm"` (`ConfirmModal.astro:57`) everywhere, which is right — the
Restore dialog's seven-row `<dl>` plus two alerts is the densest thing in the product and it holds
together because it is a definition list rather than prose. The bespoke Docs dialog uses
`py-3 text-sm opacity-80` (`SchemaDocs.astro:266`) — one hand-rolled paragraph where every sibling
dialog uses the shared body slot. `NEEDS-MEASUREMENT`: whether the Docs dialog's width matches the
`sm` modal the other eight use (mechanism: `Modal.astro` size class vs the bare `<dialog class="modal">`
here, which inherits daisyUI's default `modal-box` width — the two are unlikely to be equal).

### Ruling 1 — D30's reference

**It does not hold. D30 must re-point.** `SourceDetailView` fails the contract it was relayed as the
reference for: `SourceDetailView.astro:319-321` routes the `Read` segment straight into `setMode('read')`,
which does not call `paintValue` and does not restore `entryValues`, while `Cancel` (`:323-326`) and
Escape (`:335-341`) both restore. Because `entryValues` is re-captured on every entry into edit
(`:309`), one trip out through the segment permanently rebases what `Cancel` will restore to. This is
X11-F2 and it is confirmed in source; `S23`'s "no findings" on that file is wrong and should be
corrected in place, as `PENDING-ADJUDICATION.md` anticipated.

**The replacement reference is `entityPanelController.ts:157` (`exitEdit`) with the footer anatomy at
`schemaReadBody.ts:305-314`** — which is what D30's own opening sentence already cites for the footer;
only the exit half was mis-attributed. The two measurements are in §7. D30's rule text needs one
addition it currently lacks: *the read slot must render from the draft, not from the loaded record*
(`entityPanelController.ts:142`), because that is the invariant which makes "the segment discards" safe
rather than merely defined.

### Ruling 2 — `beforeunload`

**Confirmed: 0 occurrences app-wide, and 0 `popstate`.** So no exit is gated anywhere except the
wizard's link interceptor.

**Ruling: not acceptable as a blanket state, but `beforeunload` is the wrong instrument for six of
the eight contracts.** It renders a browser-chrome dialog whose copy cannot be written, which the
charter's tone rules cannot reach, and which fires on every reload of a surface where the loss is a
half-typed name. Adding it globally would be the app shouting where it currently whispers.

**Where the guard belongs, in order:**

1. **Generalise the wizard's interceptor into a shared helper** — `IntegrationsSetupWizard.astro:862-886`
   is already surface-agnostic in everything but its selectors: it takes a `somethingToLose()`
   predicate, a dialog id, and it rewrites the confirm href. Lift it to `lib/` and mount it on the two
   surfaces that can lose authored work with no draft behind it: **`SchemaDocs`** (X11-F1 — a whole
   document) and **`ReportDefinitionView`** (X11-F3 — a definition, on a page that already computes
   the predicate as `dirty`). Those two, plus the wizard, are the complete set; the registry pages and
   the entity panel lose one field's worth of typing, for which C1's discard-on-exit is the right
   contract and a dialog would be noise.
2. **Add `popstate`/browser-Back coverage to the same helper**, because Back out of the wizard today
   walks past the guard it just built.
3. **Add `beforeunload` on those same two surfaces only, and only as the last resort** — a tab close
   or a ⌘W is the one exit a click interceptor cannot see, and losing an entire authored document to it
   is exactly the case the blunt browser dialog exists for. Not on the wizard (its loss is a set of
   re-pickable choices), not anywhere else.

## What is good here — do not touch

- **`ConfirmModal` and `CONFIRM_DESTRUCTIVE`.** One component, one destructive class constant
  (`lib/ui.ts:15`), a `confirm` slot for callers that need a custom action, and a `confirmHref` path so
  a confirm can be a plain navigation needing no JS. Eight call sites agree with it. This is the piece
  everything else in X10 should be moved *onto*, not redesigned.
- **The Restore confirm** (`RestoreView.astro:481-508`). Seven named facts in a `<dl>`, the
  snapshot caveat in a soft warning alert, irreversibility in a soft error alert, and every string
  derived from the same request object the page above renders rather than authored in the dialog. It
  is the best destructive dialog in the product and the standard the other seven should be read
  against.
- **`pattern-undo-toast` and `undoToast.ts`.** The reasoning in `undoToast.ts:15` — outcome in the past
  tense, a ghost Undo, supersession flushes the pending commit (`:89`) — and `panelStack.ts:510-520`'s
  rule that a bulk destructive verb which cannot be taken back is not shippable. Also correct:
  `ReportDefinitionView` passing `null` for the action on Run now / Retry, because a countdown bar on
  something irreversible promises a choice that does not exist (`:785-788`).
- **The wizard exit guard** (`IntegrationsSetupWizard.astro:862-886`). It ignores modified and
  new-tab clicks, ignores untagged in-wizard links, ignores same-page and cross-origin hrefs, and
  rewrites its own confirm href so it cannot trap the user inside itself. This is the mechanism that
  should be lifted and reused — it does not need improving, it needs mounting in two more places.
- **`setButtonLoading`** (`lib/ui.ts:47-59`). Twelve lines, disables the control, sets `aria-busy`,
  injects and removes the spinner. Do not replace it with the `Button` `loading` prop; make the catalog
  describe *this*.
- **The running-status spinner inside a status badge** (`BackupsListView.astro:232` and six siblings).
  Consistent across every surface that shows a run, and it correctly answers a different question from
  the button spinner — *the object* is working, not *your click*. Leave it alone.
- **`exitEdit`'s one-line contract and its comment** (`entityPanelController.ts:156-157`). The whole
  of Ruling 1 rests on this line existing and being documented.
- **`Won't retry` / `Nothing to retry`** (`BackupRunDetailView.astro:530,546`, mirrored at
  `BackupRunBaseView.astro:325,338`). A permanently-failed attachment is marked and excluded from the
  retry count, so the button never promises a fix twice. That is the copy standard the `Retry` in
  X14-F2 fails to meet.
- **`Keep it` / `Keep running` / `Keep editing` / `Stay in setup`.** Cancel labels that name what
  staying preserves. Restore should join them, not the other way round.
