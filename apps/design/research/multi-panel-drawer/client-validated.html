Multi-panel Schema drawer — validating & deepening Dan's asks

Track A research pass · How shipped products solve V1–V6 · Baseout Schema section · 2026-07-09

What this is. Dan recorded a video asking us to evolve the Schema EntityPanel from today's cascading Anchor+Focus model (parent+child, cap 2, closing the parent closes the child) into independent, side-by-side, browser-tab-like panels so he can compare field ↔ field. This report checks each of his six asks (V1–V6) against real shipped products, flags edge-cases, and recommends a concrete design — with a focused recommendation for his open question (V6: max count + overflow).

Honest attribution: "What X does" = observed competitor behavior with a cited source. "Recommendation" = our call for Baseout, clearly labelled.

Executive summary

Dan's instinct is well-supported. The pattern he's describing — self-contained panels, a "+" to spawn one, cmd-click a link to open it beside the current one — is exactly how the strongest comparison tools ship today. The single closest precedent is the Cloudflare AI Gateway Playground and Google AI Studio "compare" views: each pane is a self-contained card with its own + and ✕ in its header, laid out horizontally.

  • V1 Independent close — do it. The cascade (close parent → close child) is the odd one out; every comparison UI closes panes independently. Give each panel its own ✕.
  • V2 "+" button — do it, and label it. Best precedents put a + in a panel's header (Cloudflare) or a labelled "Add panel" button (Chatbase "Add an instance"). Default the new panel to the current base / current table-all-fields.
  • V3 Base & Space starting levels — do it as a drill-down column, not a new screen. Neon, Airtable and every master-detail browser use one navigable list that drills Space → Base → Table → Field. Collapse the chrome when there's a single base.
  • V4 Cmd/Ctrl-click → new panel — do it, but it MUST have a visible fallback. This is his headline ask and the highest-value one, but it's a hidden affordance. Every product that relies on it also exposes a visible "open to the side / open in split" control (VS Code, Notion). Ship both.
  • V5 De-emphasize the table middle-layer — do it via optional/skippable, not removal. Airtable keeps the layer but lets you jump straight to fields; make table a pass-through when a field is the target.
  • V6 Max count + overflow — recommend a soft cap of 3 side-by-side, then horizontal scroll with a tab-strip overview; hard cap 5. Precedent: comparison/tab research says 3–5 is the human ceiling; browser tabs, VS Code editor groups and Postman all overflow by scrolling a strip rather than shrinking panes to unreadability. Details in V6 + the decisions table.

Today: A/B/C/D are locked into a 2-deep parent→child cascade. Target: any level can be its own independent panel in a horizontal rail; new panels come from + or a cmd-clicked reference.

V1 · Independent panels, closed independently validated

Ask: drop the cascade where closing a parent closes the child. Each panel is self-contained with its own "Close tab" ✕.

What real products do

  • Cloudflare AI Gateway Playground — two model panes side by side, each with its own ✕ (plus + and a collapse control) in its own header. Closing one leaves the other untouched. [Mobbin]
  • Google AI Studio compare — independent model panes, each with a header ✕; you add/remove freely. [Mobbin]
  • Notion — a page can be open as full page while a database row is open in Side Peek; these are independent surfaces, each dismissed on its own; nothing cascades-closed. [Notion]
  • Dovetail / Navattic record side-panels use a single explicit header ✕ to dismiss — the expected, discoverable close affordance for a detail surface. [Mobbin]

Pitfalls

  • Orphaning context. When a child no longer depends on its parent, a user can close the "Status field's table" and be left with a field panel whose origin is now unclear. Fix: each panel carries its own breadcrumb (Base › Table › Field) so it's self-explanatory after any sibling closes.
  • Losing "close all". Independent closes make clearing the workspace tedious. Provide a single "Close all" / Esc-clears-focused escape hatch.

Recommendation

Adopt independent panels. Every panel gets its own header with breadcrumb + ✕ (tooltip "Close panel", not "Close tab" — these are panels, not browser tabs). Keep Esc closing the focused panel; add a "Close all" affordance once ≥2 are open. Drop the parent→child cascade entirely.

V2 · The "+" button to open a new panel validated

Ask: a "+" opens a new panel; default lands on the same base / same table-with-all-fields.

What real products do

  • Cloudflare AI Playground — the + lives inside each pane's header toolbar, next to collapse/✕. Clicking it spawns a new pane to the right. [Mobbin]
  • Chatbase compare — uses a labelled button, "Add an instance", in the top bar rather than a bare glyph, so the action reads unambiguously. [Mobbin]
  • Postman / browsers — the canonical "+" sits at the end of the tab strip; users already read a trailing "+" as "new tab here".
  • Airtable interfaces — a record detail's "+ New field"/add controls appear in-panel, reinforcing that "+" inside a panel = add-within-context. [Mobbin]

Pitfalls

  • "+ of what?" A bare "+" is ambiguous about the starting level. Cloudflare gets away with it because every pane is the same type (a model). Baseout panels can be a Space, Base, Table or Field — so a raw "+" needs either a smart default or a tiny menu.
  • Placement collision. A trailing-strip "+" competes with per-panel "+"; pick one primary spawn point to avoid two mental models.

Recommendation

Two spawn points, one meaning ("open another panel"):
  • Primary: a trailing "+" at the end of the panel rail (browser/Postman mental model). Bare glyph is fine there because position teaches it; add a tooltip "Open another panel".
  • Default target = current context, one level up-and-out: matching Dan's ask — open the same table with all fields when you're on a field, or the same base with all tables when you're on a table. This makes "+" a fast "give me a sibling comparison surface".
  • Long-press / dropdown caret on the "+" offers "New panel at Base…/Table…" for jumping elsewhere. Keep the click path one-tap for the common case.

V3 · Base-level and Space-level starting views validated

Ask: new levels that don't exist yet — a base-level view and a space-level view; list all bases → drill into base → table → field. Single base ⇒ default straight into it.

What real products do

  • Neon — a left "Tables" list (schema/branch scoped) → click a table → rows → a right inspector for the selected row. One coherent drill-down column feeding a detail panel; exactly the Space→Base→Table→Field shape. [Mobbin]
  • Master-detail / two-panel selector pattern — a navigable list on one side, details on the other, letting users "skip through content at speed while keeping an overview". Standard for hierarchical browse. [IxDF] [WebAppHuddle]
  • Airtable Base schema — a base-level schema view that shows all tables and their relationships as an entry point above individual records. [Airtable]
  • Lightfield / Braintrust — sidebar hierarchy (Accounts → Contacts; Datasets → row) with a persistent detail panel, showing the "drill a level, inspect, drill again" loop generalizes cleanly. [Mobbin]

Pitfalls

  • Empty middle levels. A Space with one Base, or a Base with one Table, makes the extra level pure friction — hence Dan's "single base ⇒ default straight in".
  • Breadcrumb depth. Four levels (Space › Base › Table › Field) is deep; without a persistent breadcrumb users lose the thread, especially once panels detach (V1).

Recommendation

Model the drill-down as one panel whose "level" is data, not four different screens (this matches our existing EntityPanel decision — states-as-data). A panel can be a Space list, a Base overview, a Table (all fields), or a Field. Rules:
  • Every panel shows a breadcrumb Space › Base › Table › Field; each crumb is clickable and (with cmd) opens that level in a new panel — reuses V4.
  • Auto-skip singletons: single Base ⇒ Space view opens straight into the Base; single Table ⇒ Base opens into the Table. Never make the user click through a list of one.
  • Space/Base views are lists with counts + health (X tables, Y fields, N issues), not empty scaffolding — they should earn their level by summarizing.

V4 · Cmd/Ctrl-click a reference → new panel beside headline · needs a visible fallback

Ask (his "most user-friendly"): cmd-click a reference/backlink opens it in a NEW panel side-by-side, like cmd-clicking a browser link opens a new tab.

What real products do

  • VS Code — Cmd/Ctrl+Alt+click on a symbol runs "Go to Definition to the Side", splitting the editor and opening the target beside the source. Crucially, the same action is also a visible command ("Open to the Side", the split-editor button, and a right-click menu item) — the modifier is an accelerator, not the only door. [VS Code docs] [guide]
  • Notion — Cmd/Ctrl+click a page link opens it in a new tab instead of Side Peek; plain click uses the default (peek). Standard browser muscle-memory. [Notion peek]
  • Browsers (the mental model Dan cites) — cmd-click = new tab is near-universal, but UX literature is explicit that it's a hidden affordance: power users know it, most users don't; forcing/relying on new-tab behavior without a visible cue disorients people. [NN/g] [SensioLabs] [UXPin affordances]

The discoverability problem (and how the pros solve it)

Cmd-click is an implicit affordance — no signifier tells you it exists, so it must never be the only way to reach side-by-side. The winning pattern across VS Code / Notion: ship the modifier accelerator AND a visible control that does the same thing, then optionally teach the shortcut in a tooltip on that control.

Recommendation

Ship V4 exactly as Dan wants — and make it discoverable three ways:
  • Accelerator: Cmd/Ctrl+click (and middle-click) any reference, backlink, linked-field, relationship, or breadcrumb crumb ⇒ opens that entity in a new panel to the right, without disturbing the current one. Plain click = navigate the current panel (or its focus child, per today's behavior).
  • Visible fallback: on hover, references show a small "open beside" ⧉ icon (like GitHub's/VS Code's split glyph). Clicking the icon does the same as cmd-click. This is the signifier the shortcut lacks.
  • Teach it: the ⧉ icon's tooltip reads "Open in new panel · ⌘-click". One-time coach-mark the first time a user opens a second panel.
  • Consistency guard: because plain-click already navigates, be careful the two behaviors don't surprise — document that plain=replace-in-place, modifier/icon=open-beside, and keep it identical everywhere (breadcrumbs, refs, list rows).

V5 · De-emphasize / make optional the middle table view validated (soften, don't delete)

Ask: the table-level view is a middle layer he'd like to make optional.

What real products do

  • Airtable — you can press space to jump a row straight to its expanded record; the "table" is a pass-through, and record detail can even be swapped for a custom interface page. The layer exists but never blocks getting to the record. [Airtable expanded records]
  • VS Code / IDEs — "Go to Definition" jumps you straight to the symbol; you don't stop at the file's outline first. The intermediate structure is available (Outline view) but optional.

Recommendation

Keep the Table panel (it's the natural target for "compare all fields of two tables" and the default V2 spawn), but make it a pass-through when a field is the real target: cmd-clicking a field reference opens the field panel directly, not the table. Offer a per-user default ("open references as: Field detail / Table with field highlighted"). So: not removed, just never mandatory — matches Airtable's "layer present, never in the way".

V6 · Max panel count + overflow strategy his open question — recommendation below

Ask: he flagged this as unresolved and mused about "some kind of layering" when too many are open, each scrollable.

What the evidence says

  • Human ceiling is ~3–5. Comparison and tab research repeatedly lands on 3–5 as the point past which side-by-side/tabs overwhelm; two-panel is the comfortable default, more than that needs deliberate handling and wide screens. [Eleken tabs UX] [SAP Fiori comparison]
  • Side-by-side needs width. Master-detail side-by-side is "more suited for wider screens"; below a width threshold you fall back to overlay/stacked. [master-detail]
  • How shipped comparison tools cap: Cloudflare/Google AI Studio/Chatbase compare keep panes to a small horizontal set and let each pane scroll internally; they don't shrink panes to unreadable slivers. [Cloudflare]
  • How tab-based tools overflow: browsers, Postman and VS Code editor groups keep a fixed minimum tab/pane width and scroll the strip (with an overflow menu / tab overview) rather than infinitely subdividing.
  • Dan's "layering" intuition maps to the macOS/tab-overview idea: when too many are open, show a compact strip/stack you can flip through, each panel still fully scrollable when focused.

Recommendation for V6

Soft cap 3 visible side-by-side · hard cap 5 open · overflow = horizontal scroll of fixed-min-width panels + a tab-strip overview. No true z-axis "stack".
  • Fixed minimum panel width (e.g. ~360–420px). Panels never shrink below legible; instead the rail scrolls horizontally once total width exceeds the viewport. This is the browser/Postman/VS Code model and preserves "each scrollable" (each panel scrolls its own body).
  • Show up to 3 comfortably on a typical laptop; a 4th/5th are reachable by scrolling the rail. A slim panel-strip header (little chips: Status · Owner · Tasks · …) sits above the rail so you always see everything open and can click a chip to scroll it into view — this is the "overview" Dan wants without a literal stack.
  • Hard cap at 5. Opening a 6th prompts "Close a panel to open this" (or auto-closes the oldest/least-recently-focused, with an undo). Prevents the "40 tabs" mess and keeps compare meaningful.
  • Prefer scroll-strip over z-layering. A literal stacked/layered deck hides panels behind panels — bad for the core job (compare side-by-side at a glance). The chip-strip gives the awareness a stack would, while keeping comparison visible. If Dan still wants a "collapse to spine" affordance, implement it as a per-panel collapse-to-rail-chip (Cloudflare has a collapse control), not a global stack.
  • Narrow screens: below ~2-panel width, fall back to one panel at a time with the chip-strip as the switcher (the responsive master-detail fallback).

Refinements & new ideas we found (worth stealing)

Per-panel breadcrumb = the glue

Once panels are independent (V1), the breadcrumb inside each panel is what stops them becoming orphans. Make crumbs cmd-clickable to spawn that level (ties V3+V4 together).

"Open beside" hover glyph

The ⧉ split icon on hover (VS Code) is the single highest-leverage addition — it makes the hidden cmd-click affordance visible and teachable in one control.

Panel-strip overview chips

A chip row naming every open panel doubles as the overflow control (V6) and a "close all / jump to" surface. Cheap to build, solves awareness.

Sync-scroll for true compare

Cloudflare/AI-Studio compare panes offer a "sync" toggle so scrolling one scrolls both. For field↔field compare (same schema shape), an optional "align sections" could line up Description/Relationships/Health rows across panels.

Pin vs. transient panels

Borrow VS Code preview tabs: a single-clicked panel is transient (replaced by the next single-click); double-click or edit "pins" it. Keeps casual browsing from piling up panels while still supporting deliberate compare.

Deep-link / shareable panel set

Encode open panels in the URL (like our ?fixture= harness already does) so a field↔field comparison is shareable with a teammate — a real differentiator for an inspection tool.
