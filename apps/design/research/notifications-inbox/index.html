Notification / Inbox center

What to build, where it lives, and which signal goes to which surface.

The one-paragraph answer

Build a non-modal side panel that opens beside the work area from an Inbox item in the sidebar — Notion's posture, not Linear's. Split the list into Needs attention and Activity, because our alerts are heterogeneous and a flat list (Linear's actual weakness) buries the one row that matters. Roll up successful backups per base; never roll up failures, breaking schema changes, or reconnect. Make connection and health alerts self-healing — when the user reconnects, the alert and the banner clear themselves, silently.

1. The naming trap: “like Linear” means the opposite of what we want

Linear's Inbox is not a side panel. It is a full nav destination rendering a two-pane master–detail: a middle notification list and a right pane holding the selected issue's full detail. So the phrase in the Slack thread — “an INBOX item like Linear” — literally describes the heavy full-page surface we are trying to avoid.

The pattern actually being described is Notion's: Inbox sits at the top of the sidebar with an unread count, and clicking it opens a second column between the sidebar and the page, pushing the page narrower rather than covering it. Notion lets you lock it open while you work, and ships a chevron that expands the same panel into a two-pane view — so peek and “full inbox” are one surface, with no route change. Notion reports the lock-open change measurably increased how often people check it.

Worth flagging to the client

If we say “like Linear” and then ship a side panel, fellars will compare against Linear and see a mismatch. Better to name the reference precisely: Notion's Inbox panel, with Vercel's alert-row anatomy.

2. What the direct competitors actually do

The category finding is blunt: backup and ETL tools have no in-app inbox. They push to email/Slack/webhook and reserve the dashboard for diagnosable errors. That is simultaneously our opportunity and a warning — we are defining this pattern, not copying a proven one, so the interaction model must be borrowed from productivity tools and only the what-to-notify from the backup category.

4. The information model — three surfaces, one rule each

We already own three places a signal can land: a toast, the inbox, and the ConnectionHealthBanner. The design literature (Carbon, and the ARIA live-region guidance) gives a machine-checkable test for the first split:

If a notification carries an interactive element, it must not be a toast. A toast is a passive live region that auto-dismisses in ~3–5s and moves no focus — so anything requiring a decision has to be persistent. That single rule separates toast from inbox.

Governing rules

  • The banner means exactly one thing: a broken connection that undermines “is it working right now.” It is the loudest surface — reserve it. Let health dips or schema drift in and it stops meaning “act now.”
  • Toasts never carry a decision. If the user must choose, it is persistent.
  • The inbox is the union of actionable alerts and FYI activity, visually split. Linear's docs describe no visual distinction between actionable and FYI — everything lands in one list. That is the thing to improve on, not copy.
  • Reconnect appears in both the banner and the inbox. The banner is the interrupt; the inbox is the record. Resolving it clears both.

5. The flood problem — nightly backups will bury everything

This is the single biggest risk for a backup tool. A daily backup per base, times N bases, drowns the one row that mattered. The guidance converges:

  • Group by an entity key, not globally. “3 backups completed for Sales CRM”, not “37 backups completed.”
  • Critical alerts bypass batching. Failures and broken connections are instant and standalone; only successes digest.
  • Don't notify about expected states (Airbyte's “queued syncs” defaults to off).
  • Per-entity subscription is the flood valve — per base: All runs / Failures only / Off.
  • Health scores must be debounced — report net movement over a window, or we invent our own flapping-alert problem.

Implementation note: “batch-on-read” (collapse at render time) is the pragmatic build and is all a fixture-driven prototype needs.

6. Read, done, and self-healing

Two questions that good products keep separate.

Does opening mark it read?

Yes in both Notion and Linear — but read ≠ resolved. GitHub explicitly decouples Done from read, and that separation is exactly what lets an inbox function as a task list. We want both states.

Does fixing the problem clear the alert?

Not for free. GitHub does not auto-resolve a notification when the issue closes. The precedent comes from incident tooling instead: when a Datadog monitor recovers it auto-resolves the linked PagerDuty incident — and, deliberately, PagerDuty does not notify on recovery. Resolution silently clears the item rather than minting a new “it's fixed!” ping. Linear's auto-un-snooze on new activity is the inverse of the same idea: state changes move the item.

Recommended: a graded resolve model
  • State-backed alerts self-heal. Reconnect and health are bound to live state — when the user reconnects, the alert resolves and the banner disappears. A stale “reconnect!” after you already reconnected is precisely the trust-eroding bug this product cannot afford.
  • Resolve silently. Show a quiet “Resolved” state on the existing row; do not mint a new one.
  • Event alerts are acknowledge-based. A failed backup describes a past event — a later success does not un-happen it. The user marks it done; we may annotate “later run succeeded.”
  • Deep-link everything to the exact surface: the failed run's log, the schema diff with the breaking flag, the connection's reconnect flow.

7. Accessibility (a non-modal panel has different rules)

  • A non-modal side panel is not a role="dialog". Don't trap focus, don't steal focus on open. Make it a labeled complementary region reachable by shortcut. Focus-trap and aria-modal belong only to modal overlays.
  • Announce arrivals through a polite live region (“1 new notification”); reserve assertive for failed-backup and broken-connection.
  • Keyboard triage, borrowing Linear's vocabulary: open/focus the panel, J/K to move, U read-toggle, E done, Esc returns focus to the trigger.

8. What this means for our catalog

Good news: the behavior is already sanctioned. pattern-multi-panel-drawer (the Schema EntityPanel) is already non-modal — no scrim, content behind stays visible and clickable, with a resize shutter and a width persisted in localStorage. The drawer primitive, by contrast, is modal (drawer-overlay scrim) and is the wrong base for an inbox.

So the build is: one new storybook.ts entry (pattern-inbox), inheriting the non-modal posture, plus a fixture. No invented components.

9. Decisions to lock before building

D1
Push or overlay? Notion pushes the content narrower; incident.io overlays and dims. Push is the admin-appropriate choice and matches our existing decision to keep the banner inside the work area.
D2
Sidebar Inbox item, and where? Above the Space group (it is account-scoped, not Space-scoped) or inside it? Note the client is also adding a Data item and moving Restore down.
D3
Needs attention / Activity — tabs or two sections in one scroll? Sections keep the count visible without a click; tabs scale better if volume grows.
D4
Triage vocabulary. Minimum is read/unread + Done. Do we also want Snooze (Linear) and Mute-this-base (incident.io hover action)?
D5
Full-page inbox — does it earn its keep? Notion expands the panel in place via a chevron; incident.io ships a separate Alerts page for history. Given our alert volume, expand-in-place is probably enough.
D6
Which rows get an inline action button (Reconnect · View log · Review diff) versus deep-link-only?
D7
Topbar fate. If the Inbox moves to the sidebar, the bell disappears — and the connection-health pill (which lives in topbar-status) loses its home. The topbar then holds only a mobile-only hamburger.
D8
Rollup thresholds and the health-score debounce window. No external number to cite — judgment call, tune with the client.

Honest gaps

  • Rewind / BackupSheep notification UX: unverified. No authoritative docs found.
  • Self-healing is a cross-domain transfer, from incident tooling — no backup tool was observed doing this in an in-app inbox. High upside, low risk to prototype, but it is our invention, not a copied pattern.
  • No direct competitor validates an in-app backup inbox at all. The category lives in email. We are defining the pattern.
  • Digest thresholds and debounce windows have no citable number. Set by feel, tune with the client.
  • Airtable ships often — re-check the bell's behavior before mirroring it. The load-bearing point (bell = social, not operational) is robust.
