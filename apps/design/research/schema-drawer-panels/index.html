Holding many contexts without losing your place

The question isn't "how should a drawer behave" — it's how a power user holds several related schema entities at once, pins some, arranges them, and stays oriented. A survey of six paradigms (terminals, IDEs, canvases, CRMs) and where they land for us.

Reframing the problem

Not "a drawer" — a way to keep working across many entities

A schema is a dense reference graph: a field references many fields and is referenced back by automations, formulas, rollups, lookups, pages. Following one thread spawns another. The real job:

Let the user open several related entities, keep the ones that matter visible, arrange them (side-by-side / stacked), switch between them, and never lose the thread they were pulling.

Your own analogy — a terminal multiplexer: split panes, switch focus, tile or stack, zoom one full and back. That's the right instinct; the trick is importing its power without importing its complexity onto the web and onto non-power-users.

The finding that decides everything

Three independent research tracks converged on one idea

Preview vs. Pinned

Dev-tools (VS Code's preview tab vs pinned tab), knowledge tools (Roam's pin to sidebar), and B2B apps (Qatalog Pins, Salesforce closable tabs) all independently split panels into two classes: most are transient — you glance and discard while following references — and a few are worth keeping.

This is the answer to the trap in "just let me open everything side by side": unrestrained tiling drowns you in panels. Make the default a single reused preview, and let the user promote the few worth holding. Every strong recommendation below is built on this distinction.

Live proof

The tile paradigm is already shipped — in Airtable

Dan's clip is direct evidence for paradigm 03: drilling a linked record opens a second full panel beside the first, each resizable, up to ~3 side-by-side. Not a mockup — production behavior in the tool our users already know.

Recommendation

One layered model: Peek → Pin → Tile

Don't pick one paradigm — layer three, gated by effort so casual use stays simple and power users get the terminal-like control. Each layer is opt-in on top of the last; the default is just today's drawer.

Layer 1 · default
Peek

Click an entity → one preview panel that reuses its slot as you follow references. Cheap to open, cheap to dismiss. This is 90% of navigation and it's what we already ship. Peek → full-page toggle escapes the modal trap.

Layer 2 · hold
Pin / keep open

An explicit Pin promotes a peek to persistent. Held entities live as a tab strip or a collapsible stack — open many, reorder, close individually. This is your "keep some handy" and it survives navigation.

Layer 3 · arrange
Tile + zoom

Put 2–3 pinned panels side-by-side with drag-resize (Airtable / VS Code), and zoom one to full and back (tmux) to deep-read a long field list then snap to the arrangement. Cap 3 visible; overflow → tabs. Collapses to Layer 1 on mobile.

Two escape hatches, not core

Miller-columns option for pure linear drills (trace one chain with the path lit), and the existing graph / Visualize tab as the launcher you open panels from (dbt Explorer's "click node → detail") — never the reading surface. Canvas stays out.

Intellectual honesty

Where we're inventing, and what to verify

The honest gaps

  • No one ships the full combo. Pin (Qatalog) and arbitrary side-by-side (Cloudflare) are each proven — but never together in one product. We'd be composing proven primitives into a mildly novel whole. Defensible, but prototype before committing.
  • Genuine N-up side-by-side of arbitrary entities is unclaimed in mainstream B2B — every "side-by-side" hit is a fixed 2-up compare/playground (clustered in dev/AI tools, our adjacency). Airtable's resizable records is the closest real precedent.
  • Two load-bearing claims are reported, not hands-on verified: that Notion/Linear won't hold multiple peeks at once, and that Roam's sidebar comfortably holds "as many as you want." Worth a 15-minute hands-on before locking the pattern.
  • Mobbin is static — resize/drag/reorder were inferred from visible handles, not observed. The Airtable interaction, by contrast, we saw live in the clip.

Before we build

Decisions to lock

  • Hold mechanismPinned stack/rail (Roam) or closable tab strip (Salesforce) for held entities? Tabs = lower novelty; stack = more visible at once. Could do tabs first, stack later.
  • Tile triggerDrilling always opens beside (Airtable), or only an explicit "Open beside / Pin" spawns a second panel? Recommend explicit, so default stays a single peek.
  • Resize modelFree drag (Airtable) or snap widths ⅓/½/⅔? Snap is tidier + simpler; free-drag matches the reference.
  • Visible capHard cap 3 tiled; overflow to tabs; zoom for deep-read? Recommended.
  • Scope nowShip the layered model in Schema only, or design a general app-wide drawer/panel primitive?
  • Next stepPrototype the Peek→Pin→Tile flow on the real SchemaView to react to, before committing build? Strongly recommend.
