The short version

Verdict up front

Correction to my earlier note: this replaces the read from the field-detail video. Dan is explicitly asking for resizable, side-by-side multi-panel navigation — not a conservative single-drawer back-stack. The research still holds; the recommendation shifts toward building it.

Dan's ask, in his words: "they have the ability to drag this out… you could almost have multiple things showing… multiple layers deep… instead of expand-halfway they let you pick the size… three open fields side by side." He wants to keep our back button, and add Airtable's two moves: (1) drag-to-resize each panel to any width, and (2) drilling a link opens a new panel beside the current one, so several stay visible at once.

Good news: this is a shipped, proven pattern (Airtable itself; VS Code editor groups) — not the unshipped "draggable floating drawers" my earlier research warned about. The design-system warnings are about overlay-nested drawers; side-by-side docked panels dodge those pitfalls because every panel stays fully visible with clear separation. Recommendation: build the Airtable model (Option B), capped at ~3 visible panels, degrading to our current single-drawer back-stack on narrow screens.

Research (still valid, reframed)

Does the evidence support stealing it?

Two research passes (competitor/design-systems + Mobbin) — reframed against what the clip actually shows. The earlier caution was aimed at overlay-nested drawers; Airtable's side-by-side docked model is a different, safer animal, and it's shipped.

Supports building it

  • Airtable ships it — the exact pattern, in production, for exactly this "record references record" job.
  • VS Code editor groups — resizable docked splits users keep 2–3 of; proven and loved.
  • Side-by-side beats overlay: the layered-drawer A/B study found deep overlays disorient; keeping panels fully visible with clear separation is the fix Dan is already pointing at.
  • Rox / Attio / Sentry — multi-pane inspectors show simultaneous panels are a normal power-user expectation.

Constraints to respect

  • Cap the visible count. Beyond ~3 panels, widths collapse to unusable — Airtable is bounded by screen width in practice.
  • Figma reversed floating/movable panels — so keep panels docked, not free-floating. Resize yes; tear-off no.
  • Mobile has no room for two panels — must collapse to our single-drawer + back-stack.
  • Design systems warn on nesting (NewsKit, Carbon, PatternFly) — a spatial tile with independent back buttons sidesteps the focus-trap trap.

If we build B

How the interaction should work

  1. Open

    Click an entity → one docked panel on the right (today's behavior). This is the default and the only panel on mobile.

  2. Drill a reference

    Click a reference / linked row → a new panel opens beside it. Panels read left-to-right as a trail; the newest gets focus. (Airtable opens the new one to the left of the origin — we pick one direction and stay consistent.)

  3. Resize

    Drag any divider to rebalance. Enforce a min width (readable ≈ 320px) and remember the user's sizes per session.

  4. Cap & overflow

    Max 3 visible. A 4th drill collapses the oldest into a thin clickable spine (its name rotated / a breadcrumb crumb) — nothing is lost, screen stays usable.

  5. Close / back

    Per-panel close and per-panel back (keep our back button). Esc closes the focused panel; closing collapses the row leftward.

  6. Collapse on mobile

    Below a breakpoint, only the focused panel shows full-width; the rest become the Option A breadcrumb back-stack.

Before we build

Decisions to lock

  • Open directionNew panel opens to the left (Airtable) or to the right of the origin? Pick one and keep it consistent — affects reading order of the trail.
  • Visible capHard cap at 3 panels, oldest collapses to a spine? Recommended — beyond 3, widths break.
  • Resize modelFree drag with a 320px min, or a few snap widths (⅓ / ½ / ⅔)? Free-drag matches Airtable; snaps are simpler + tidier.
  • What can spawn a panelOnly linked-record / relationship rows, or any reference (formula refs, referenced-by) too? Recommend: any chevron row, so the whole graph is traversable.
  • PersistenceRemember open panels + widths across navigation / reload, or reset each visit?
  • Mobile breakpointConfirm the width below which we drop to single-panel + back-stack.
  • Scope nowShip B in Schema only first, or design it as a general drawer primitive for the app?
