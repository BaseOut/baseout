Navigating a schema that references itself: drawer options for the field detail panel

Grounding Dan's video feedback in the actual UI, then answering the real question underneath it — how does a user traverse a field's references and back-references without losing their place — backed by competitor + Mobbin research.

Source: 10:51 walkthrough feat/drawer-stacking Web + Mobbin research 2026-07-07

The short version

Verdict up front

The video is not really a request for draggable, rearrangeable stacked drawers. Dan is asking for three concrete things: (1) stop truncating what a formula/lookup references, (2) show the reverse — what references this field — and (3) let him jump back and forth through that reference graph without getting lost. "Open many panels and swap them around" is our framing of the underlying need, not his ask.

Both research tracks land in the same place: no shipping B2B tool offers user-rearrangeable multi-drawers (and Figma actively retreated from movable panels). The proven vocabulary is one focused drawer + a breadcrumb back-stack + a sibling pager + hover-peek — most of which our drawer already has. So the recommendation is to finish the model we started, add a bounded 2-deep "open beside" for the one genuine compare case, and treat rearrangeable tabs as an explicit, clearly-labelled experiment — not the default.

Everything Dan raised

The findings, sorted by what they actually are

Three of these are the navigation thesis; the rest are polish, some already handled by recent drawer commits.

  1. Show the reverse of every reference navigation

    "Looked up by / rolled up by / referenced by." Group all inbound references in one Relationships section, each row carrying its type (formula ref, rollup, lookup, automation, page, chat) and a direction indicator. This is the headline ask.

  2. Jump back and forth without losing place navigation

    "I want to quickly jump back and forth and see where it's being referenced." Traverse field → referenced field → back, keeping a trail. This is what surfaced the "stack / swap panels" idea.

  3. Stop truncating references navigation

    A formula references two fields but the row shows one. Show up to ~3, then +N more (a formula can reference 50). Hover = quick peek of the rest; click = open that field.

  4. Worst-case data / in-panel navigation density

    Long descriptions (grow, then scroll), long formulas, long changelogs. Consider an Airtable-style section-tab header that scroll-jumps within the drawer.

  5. Trim the top-level table columns density

    Cardinality / Link columns aren't worth the width for link-type rows — keep Type, drill in for the rest. Buys room for more useful signals (e.g. "tagged").

  6. The synced-copy warning icon looks like an error visual

    Swap the ⚠ for a neutral/info glyph; align the "synced" and "shown to everyone" lines.

  7. Reference count alignment visual

    Counts sit too close to their label and read as "references to". Right-align them.

  8. Section separation & hierarchy recently addressed

    Sections "blend together"; Configuration nesting is ambiguous. Recent drawer commits already moved toward whitespace-separated sections and a standardized identity line — worth confirming against this video.

  9. "Tagged in" preview density

    Tagged in a doc or chat → hover preview with an icon per type; if tagged in several, make each reachable.

Research

What shipping products actually do

Two independent passes — competitor/design-system web research and a Mobbin pattern sweep — converged hard. The honest headline: the rearrangeable-multi-drawer idea is essentially unshipped, and the field is dense with a different, proven pattern.

Web / design systems

  • Linear Peek — one overlay, Space/Esc, ↑↓ steps siblings in place. The density-first default.
  • Layered-drawer A/B study — deep nesting made users "feel lost"; a 2-deep peek with the parent still visible tested better.
  • Design systems warn against nesting: NewsKit ("avoid nesting tiered drawers"), Carbon (no nested modals), PatternFly (single-drawer only). MUI/Ant treat nested drawers as bug-prone.
  • Figma UI3 reversed floating/movable panels back to fixed — a direct caution against "rearrange your panels."

Mobbin

  • Airtable — expand-record with a ‹ › sibling pager; a linked record opens a new layered card (drill, not tile).
  • Rox — two genuinely stacked overlays with the first dimmed behind: the visual language for "there's a panel behind this."
  • Coda / Attio — right drawer titled "Row from <Table>" + a "1 of 3" pager. The single most common model.
  • Productboard — peek drawer → expand to full page (mirrors our Ask → drawer → expand pattern).
  • Honest gap: Mobbin showed no drag-reorder / pin / swap of parallel drawers anywhere.

The decision

Four navigation models

A Single drawer + breadcrumb back-stack Default — mostly built

One drawer. Drilling a reference pushes into the same panel, breadcrumb grows, back pops. Add a sibling pager (step through peers in the current list) and hover-peek on reference rows. Our drawer already has the breadcrumb and expand — this is finishing, not starting.

Zero screen cost, keyboardable, no focus/z-index hazards
Serves "jump back and forth" + the back-references directly
Can't show two entities side-by-side
Deep trails need breadcrumb truncation

Ref: Linear Peek · Coda · Attio · Squarespace

B Bounded 2-deep "open beside" peek Add for compare

An explicit Open beside action spawns a second drawer over the first, parent edge peeking; click the parent to swap forward. Hard cap at 2 (max 3); collapses to A on mobile. This is the honest, capped version of "keep both open" — for the one real job: field ↔ its linked table.

Genuine side-by-side without unlimited nesting
Backed by the A/B study + Rox/Airtable layering
Focus-trap + z-index complexity
Must degrade on narrow viewports

Ref: layered-drawer study · Rox · Airtable linked-record card

C Held-open entity tabs (pin & reorder) Experiment only

Browser-tab-style chips of opened entities above the drawer; click to switch, drag to reorder, pin. This is the literal "open many panels and swap them around." It's also the one model no B2B tool ships — build it only if telemetry shows users genuinely hold >2 entities, and label it as experimental.

Closest to the raw ask; supports many held entities
Reuses our tab vocabulary
Unproven; Figma retreated from movable panels
Reorder + persistence + focus = real cost

Ref: none shipping — novel extension

D Miller columns (cascading rail) Not for detail

Finder-style columns for Base → Table → Field. Good for drilling the hierarchy with the path visible — but the schema is a cross-linked graph (Relationships jump sideways), which columns model badly. At best an optional Browse layout, never the detail surface.

Whole drill path stays visible; good lateral sibling jumps
Breaks on cross-links; narrow columns; weak a11y

Ref: macOS Finder · X settings

Recommendation

Finish A, add B, gate C, skip D

Ship A as the everyday model — it's ~80% built and it's what the video is really asking for. The two features that turn it from "detail panel" into "navigable graph" are the back-references / Relationships section (finding 1) and hover-peek + sibling pager (findings 2–3).

Add B behind an explicit "Open beside / Compare" affordance, capped at two visible drawers, degrading to A on mobile. That satisfies the legitimate "keep both open" need without the nesting hazards every design system warns about.

Hold C as a labelled experiment. It's the most literal reading of the brief and the least supported by evidence — worth a prototype to react to, not a default to build blind. Skip D as a detail surface; revisit only as an optional Browse layout.

Before we build

Decisions to lock

  • Default drill behaviorReplace-in-place (A) as default, "Open beside" (B) as an explicit action? Recommended — matches every proven reference.
  • Cascade depthHard cap the visible cascade at 2 (absolute max 3)? Beyond that, fold into the breadcrumb history so nothing is lost.
  • Back-references shapeOne grouped "Relationships" section (by type, with a direction indicator) vs. inline per config block? Recommend the grouped section.
  • Sibling pager scopePager steps through the current list/table's rows, or the current filter result? Recommend the visible filtered set.
  • Truncation ruleShow 3 references, then +N more; hover peeks, click opens? Confirm the number (3) and the hover contract.
  • MobileCollapse to a single full-width drawer + breadcrumb; never two stacked drawers on narrow screens.
  • Prototype C?Do we spend a prototype on held-open entity tabs to react to, or park it until telemetry justifies it?
