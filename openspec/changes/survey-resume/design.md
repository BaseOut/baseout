# survey-resume — Design

## Context

`apps/survey` is a standalone Astro app deploying to Cloudflare Workers (`baseout-survey`, target survey.baseout.com). Today: answers in `sessionStorage`, one `POST /api/submit` at the end (stubbed), D1 binding declared-but-commented, dual adapter (Node in dev, Cloudflare on deploy). The owner's UX requirements: email asked up front with **zero verification friction** to start; verification (magic link) only for cold resume. Baseout product convention is passwordless (better-auth magic link) — the survey reuses that stack.

## Goals / Non-Goals

**Goals:**
- Respondent can close the tab, come back days later (same or different device), and land on their saved step.
- No verification gate at start — email in, straight to question 1.
- Server-side autosave from the email step onward; the survey becomes partially-captured data by design.
- Zero-setup local dev preserved (miniflare D1 via `platformProxy`).

**Non-Goals:**
- No password auth, no OAuth, no account management UI — this is a survey, not the product.
- No merge/conflict UI when the same email starts on two devices without logging in (last-write-wins; see Risks).
- No change to the report dataset shape: analysis still reads completed submissions; partial rows are operational data, not report data.
- Provisioning `responses`/`partner_interest` + real completion tokens stays in survey-app task 2.1 (this change provisions the *database* and the auth/progress tables only).

## Decisions

1. **better-auth with `anonymous` + `magicLink` plugins.**
   - *Start path:* `signIn.anonymous()` issues an instant session (no email round-trip); the entered email is stored on the progress row, **not** as verified auth identity. This is the documented better-auth pattern for "start now, authenticate later."
   - *Cold-resume path:* `signIn.magicLink({ email })` — clicking the emailed link creates/signs into the user for that email; the server then attaches the progress row(s) matching that email (verified ownership) to the new session.
   - *Alternative rejected:* creating a real user + session directly from the unverified email (no anonymous plugin) — would let anyone hijack a respondent's in-progress answers by typing their email; anonymous-session + email-as-data avoids that while keeping friction at zero.
   - *Alternative rejected:* signed resume-token links without better-auth — less code, but the owner explicitly wants better-auth email login, and it matches the product stack.
2. **Session lifetime 30 days, cookie-based** (better-auth default cookie session; `expiresIn` 30d, `updateAge` 1d). Most respondents resume within days; the magic-link path covers the rest.
3. **Storage: D1 + drizzle adapter.** better-auth core tables (`user`, `session`, `account`, `verification`) via better-auth's drizzle adapter over `drizzle-orm/d1`, plus `survey_progress`: `(id, user_id FK, email, survey_version, answers TEXT/JSON, step_idx, updated_at, completed_at)`. Non-unique index on `(email, survey_version)` — duplicate rows from two anonymous devices are allowed and resolved by recency at verified-resume time (simpler than upsert-conflict handling; a survey tolerates last-write-wins). Migrations are plain SQL under `migrations/`, applied with `wrangler d1 migrations apply` (local + remote).
4. **Resume matching is by email, adopt-on-read.** Rather than an auth-plugin hook, `/api/progress` itself resolves ownership: for a session whose email better-auth has verified, the most-recent row matching that email is re-pointed to the verified `user_id` on first read/write. Same guarantee, less plugin coupling, and it's exercised by the endpoint's own tests/smokes.
5. **`/api/progress` endpoint (session-gated).** `GET` returns `{answers, stepIdx, completed}` for the session's progress row; `PUT` upserts. Autosave fires on every Next/Back with `keepalive: true` fetch; `sessionStorage` stays as the optimistic local cache so the UI never blocks on the network.
6. **Email delivery: Resend HTTP API via fetch.** No SDK dependency. `sendMagicLink` falls back to `console.log`ging the URL when `RESEND_API_KEY` is absent (local dev) — the standard stub-in-dev pattern for this repo. From-address decision deferred to deploy (needs the survey domain's DNS).
7. **Adapter: Cloudflare always — `@astrojs/cloudflare` v13 (the Astro 6 line).** Replaces the Node/Cloudflare dual switch — the app needs `env.SURVEY_DB` in dev, and the v13 adapter runs `astro dev` inside workerd (@cloudflare/vite-plugin) with a local miniflare D1, zero setup. Env access is `import { env } from 'cloudflare:workers'` (locals.runtime.env is gone in this adapter line); binding types are generated by `wrangler types` (the typecheck script runs it). **Version trap discovered during implementation:** the scaffold pinned adapter v14, which peers Astro ^7 and crashes `astro dev` on Astro 6 with `Could not resolve "cloudflare:workers"` — the v13.x line is correct for Astro 6.
8. **Flow placement of the email question:** the email step becomes a dedicated first screen ("Where should we send your copy of the report? We'll also save your progress so you can finish later.") — honest about both uses. The question bank's trailing email question (G4-equivalent) is dropped from the flow and prefilled from the start-step email at submit time.

## Risks / Trade-offs

- [Unverified email at start → someone could enter an email they don't own] → That only pollutes *their own* anonymous session's progress; reading or claiming existing progress always requires the magic-link (verified) path. Worst case: a bogus row that last-write-wins cleanup supersedes.
- [Two devices, both anonymous, same email → divergent progress rows] → Unique `(email, survey_version)` upsert makes the second device's first save adopt-or-supersede by recency; acceptable for a survey (last-write-wins), documented in code.
- [Autosave adds a network write per step] → `keepalive` fetch, fire-and-forget with local cache fallback; D1 single-row upserts are well within free-tier limits at survey scale.
- [Adapter switch could disturb designer zero-setup dev] → `platformProxy` needs no account/login; verify `pnpm --filter @baseout/survey dev` boots clean on a fresh clone before closing the change.
- [better-auth on Workers + D1 maturity] → pin versions; smoke the full anonymous → magic-link → resume path in `wrangler dev` before deploy. Repo `minimumReleaseAge` may require `--config.minimum-release-age=0` at install (documented gotcha).

## Migration Plan

1. Land code + migrations; `wrangler d1 create baseout-survey`, paste `database_id` into `wrangler.jsonc`, `wrangler d1 migrations apply` (local, then remote).
2. Set secrets: `wrangler secret put BETTER_AUTH_SECRET`, `wrangler secret put RESEND_API_KEY`; deploy.
3. Rollback: the feature is additive — reverting to the sessionStorage build loses resume but breaks nothing; D1 tables are inert.
