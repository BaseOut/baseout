# system-staging-readiness

> **Companion changes**: [`shared-managed-r2-staging`](../shared-managed-r2-staging/proposal.md) (owns the R2 bucket/token ask + backup verification protocol — NOT duplicated here), [`system-db-migrations`](../system-db-migrations/tasks.md) (owns the migrate-on-deploy wiring; its unchecked Phase 4 dashboard tasks are folded into this change's Dan ask). Audit sources: end-to-end sweep of the `staging` branch (2026-09-01, post Dan's env refactor `539318a7`→`4f1c8e46`), PRD v1.1 §20 (secrets), Features §7 (destinations), `shared/internal/ops-setup.md`, `oauth-setup.md`, `r2-setup.md`.

## Why

Dan's Aug-31→Sep-1 refactor moved the repo to a new model: one committed `wrangler.jsonc` per app with `dev`/`staging`/`production` env blocks, GitHub→Cloudflare Workers Builds deploys, root `db/migrations/` applied through a cloudflared tunnel at build time, and staging+prod on separate Cloudflare accounts. The repo side of that model is largely coherent — but staging does not actually work (magic-link email dead, Airtable refresh cron apparently inert, backups unprovable), and we have **no account access** (Cloudflare, Trigger.dev, DigitalOcean are Dan-only). An end-to-end audit found the following, split into what the repo can prove vs. what only Dan can verify:

### Root-cause candidates for the reported symptoms

1. **Magic-link email — most likely a wrong build command, failing silently.** Which wrangler env block ships is decided at **build time**: `apps/web/scripts/launch.mjs` flattens exactly one env into `dist/server/wrangler.json`, selected by `CLOUDFLARE_ENV`. The default `pnpm build` = `build:dev`, which bakes in `BASEOUT_DEV=true` — and `sendEmail` (`apps/web/src/lib/email/send.ts:16-26`) **logs instead of sending** whenever `env.dev` is true (`middleware.ts:124` + `:351-354`). If the staging Workers Builds project runs the default build instead of `build:staging`, staging silently gets: no email ever sent, `PUBLIC_AUTH_BASE_URL=https://baseout.local`, the dev Hyperdrive dummy id, the `baseout-server-dev` service binding, non-Secure cookies, and `DEV_TRUSTED_ORIGINS` on a public host. One dashboard setting explains the entire symptom. Nothing in the repo can verify it.
1b. **Verified live (2026-09-01): `console.baseout.dev` sits behind a Cloudflare Access wall** (`staging-338.cloudflareaccess.com`) — every path 302s to Access login, including `POST /api/auth/sign-in/magic-link`. Anyone without an Access session (new testers, Playwright, external probes) sees total failure regardless of the items above; and anything that must reach staging unauthenticated by Access (Airtable webhooks to `hooks.baseout.dev`, Trigger.dev task callbacks to the engine's `BACKUP_ENGINE_URL`) is dead-on-arrival if the Access policy covers those hosts. This also blocks us from externally probing which build flavor staging is running.
2. **Magic-link email — second candidate: sending domain / destinations never provisioned.** `ops-setup.md` §1 staging email is an unchecked box. The `send_email` binding (`EMAIL`) sends as `login@mail.baseout.dev` in staging; if the Email Routing sending domain isn't verified, or the binding is destination-restricted and tester inboxes aren't verified destinations, the send throws → `/api/auth/sign-in/magic-link` 500s.
3. **Airtable refresh cron — the cron triggers ARE correctly declared** in `env.staging` (`*/15 * * * *` et al., `apps/server/wrangler.jsonc:175-181`), so the wrangler config is not the problem. The two live candidates are both value-level and invisible from the repo: (a) **`BASEOUT_ENCRYPTION_KEY` value drift** between `baseout-web` (writes `*_enc` at Connect) and `baseout-server` (decrypts on refresh) — a bad key makes `decrypt` **throw after the refresh claim is stamped** (`resolve-airtable-token.ts:135-142`), so the claim never clears, every retry gets `refresh_claim_unavailable`, and no status flips — silent and permanent; (b) the server deploy shipping the wrong env block (same build-command issue as #1 — the engine has its own Workers Builds pipeline). Compounding it: the `scheduled()` loop has no per-job try/catch (`apps/server/src/index.ts:966-987`), so one throwing job kills every other job on that cron firing.
4. **Backups — the Trigger.dev Staging environment is unprovisioned.** Tasks hard-throw without `BACKUP_ENGINE_URL`/`INTERNAL_TOKEN`; the four `R2_*` vars are unconfirmed (per `shared-managed-r2-staging`); `TRIGGER_SECRET_KEY` on the staging engine must be the **Staging-environment** key (the key alone selects which Trigger.dev env runs land in — historically only a `tr_dev_*` key existed); and no Staging worker deployment exists (`trigger.dev deploy` is in no CI workflow — Workers Builds can only run wrangler).

### Repo-side defects the audit surfaced (fixable without Dan)

5. **Dead guardrails that the configs claim exist.** Twelve wrangler comments say "`pnpm secrets:check` asserts the lists match; CI fails on drift" — no such npm script exists and `scripts/check-wrangler-secrets.mjs` is wired into nothing (run manually: all 8 configs currently pass). `apps/server/scripts/check-cron-config.mjs` crashes outright (reads the deleted `wrangler.jsonc.example`) and only ever linted `env.dev`. CI (`.github/workflows/ci.yml`) doesn't even trigger on pushes to `staging`.
6. **Latent auth single-point-of-failure.** `console.baseout.dev` is absent from both `AUTH_BASE_URL.allowedHosts` and `PROD_TRUSTED_ORIGINS` (`auth-factory.ts:78-93`). It works today only because better-auth auto-trusts the `PUBLIC_AUTH_BASE_URL` origin — the moment that var is unset/empty, magic links mint against the `https://baseout.dev` fallback and CSRF rejects the staging origin.
7. **Small config bugs**: `apps/web` `env.dev` `BACKUP_ENGINE` service binding is missing `remote: true` (admin and api both have it; web's own comment says it's required); `E2E_TEST_TOKEN` is in no `secrets.required` list although `E2E_TEST_MODE=true` is set on staging (the Playwright bypass endpoints 401 with no deploy-time warning — and `E2E_TEST_MODE` on a public host is itself a security review point); ~~`apps/workflows/.env` tracked in git~~ (re-verified 2026-09-01: untracked and gitignored — original audit finding was false); prod blocks carry `"id": ""` KV/`CLOUDFLARE_ACCOUNT_ID: ""` placeholders that silently break (deferred — prod is a later change, but recorded).
8. **Stale runbooks actively mislead.** `ops-setup.md` still instructs editing `wrangler.jsonc.example` placeholders that no longer exist, names `baseout-server-staging` workers that were never created (staging pins the bare `baseout-server` name for Workers Builds), and describes GitHub Actions deploy jobs that don't exist. `cloudflare-env-separation.md` asserts the exact opposite of the current model. `apps/web/.env.example` documents `RESEND_API_KEY`, which nothing reads (email is the `send_email` binding).

## What Changes

- **One consolidated Dan ask** (single message, exact settings, no account access assumed on our side) covering: both apps' Workers Builds build commands + watch paths + the six tunnel build vars; staging email provisioning; the byte-parity secret sets (with the three-names-one-value `INTERNAL_TOKEN` contract spelled out); the Trigger.dev Staging environment (key, env vars, worker deployment); staging OAuth redirect URI registration per `oauth-setup.md` §3; a local-dev DB access path (tunnel hostname + service token, since the old dev DB is gone); and turning on Workers logs for staging.
- **`apps/web`** — auth hardening: add `console.baseout.dev` to `allowedHosts` + `PROD_TRUSTED_ORIGINS`; add `remote: true` to the dev `BACKUP_ENGINE` binding; add `E2E_TEST_TOKEN` to staging `secrets.required` (or drop `E2E_TEST_MODE` from staging — decision in design).
- **Guardrails resurrected** — wire `check-wrangler-secrets.mjs` up as the `secrets:check` script the configs already advertise, fix or delete `check-cron-config.mjs`, add `staging` to CI trigger branches.
- **Hygiene** — untrack `apps/workflows/.env`; commit the pending `apps/server/.gitignore` `wrangler.local.jsonc` line.
- **Docs reconciled to reality** — rewrite `ops-setup.md` staging sections to the Workers Builds model; mark `cloudflare-env-separation.md` superseded; remove `RESEND_API_KEY` from `.env.example`; fix the stale `baseout-server-staging` header comments in the wrangler files.
- **Staging verification protocol** — once Dan's items land: magic-link end-to-end on `console.baseout.dev`, refresh-cron health read from `service_runs`, and the backup smoke (delegated to `shared-managed-r2-staging` §5 protocol).
