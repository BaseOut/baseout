  **Checksum finding (was implicit in Decision 1, actually a gap):** the export path did NOT previously compute a content hash — dedup is by compositeId, and `AttachmentRecordEntry.contentHash` was never populated. As built: writes sha256 their in-hand bytes (Web Crypto, `sha256:<hex>`) and now ALSO stamp `contentHash` on the dedup record entry (the engine's attachments/record route already persists it); dedup-skips use the engine-returned `contentHash` when the lookup provides one (lookup types widened additively — today's engine lookup route returns only storageKey/uploadStatus) and otherwise fall back to the deterministic `att:<attachmentId>` surrogate. Surrogate assets are idempotent run-over-run and self-heal into real-hash assets once the engine returns/backfills content_hash (the orphaned surrogate asset drops to zero refs → retention).
  **Locator stability per provider (open question 2), verified against the writers:** the emitted locator is uniformly the writer's RELATIVE storage key (buildAttachmentKey) — the only locator in hand on both write and dedup-skip paths (it is also exactly what bo_at_attachments stores as storageKey). Per provider: `r2_managed` → `{kind:'r2_managed', key}` — canonical/stable (putObject writes at exactly that key). `google_drive`/`box`/`onedrive` → `{kind:'destination', provider, locator}` — the writer resolves/creates a folder chain matching the key's segments under the connected root and uploads by filename; the locator is that logical path, stable unless the user renames/moves folders in their own drive; provider-native file ids ARE returned by the upload calls (`drive://<parentId>/<file>` etc.) but are discarded by processCell today and are unavailable on dedup-skips — retaining them would need a StorageWriter interface + dedup-table widening (follow-up if the read path ever needs direct-id access). `dropbox` → path-based provider API, so the relative path IS the provider's addressing scheme — stable modulo user moves. `local_fs` → `storage` omitted entirely (bytes only staged on the runner's disk; the index still fills).
