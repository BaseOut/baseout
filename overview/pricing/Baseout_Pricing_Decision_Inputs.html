1 · The Product

Baseout is a B2B SaaS utility for Airtable platform admins. It (1) backs up Airtable automatically — schema, records, attachments via the REST API on monthly/weekly/daily/webhook-"instant" cadences (all technical capabilities of the system), plus automations & interfaces via user-submitted intake; (2) restores — base- or table-level, point-in-time, always into new bases/tables; (3) gives the data an external home — the customer's own storage (Drive, Dropbox, Box, OneDrive, S3, BYOS) or Baseout-managed storage, optionally with a live SQL database copy (SQLite → shared Postgres → dedicated Postgres → customer's own DB); (4) layers intelligence on top — schema visualization & change history, base health scoring, documentation tooling, data metrics/alerts, AI-assisted docs, analytics, and (roadmap) governance, MCP/RAG AI access, connectors. V1 is Airtable-only; architecture is built for multi-platform V2 (Notion, HubSpot, Salesforce), each platform its own subscription component under one billing relationship.

Composites the data model could also support (options, not recommendations): a single abstract usage unit unifying several dimensions (one number, flexible; but customers can't predict bills unaided — internal drafts explored this), or pure feature-tiering with soft caps (what shipped code does today).

Usage physics any metered model must handle — (1) The initial-backup spike: the first backup of a large base can be 100–200× steady-state usage; without grants/amortization the first invoice ambushes the customer. (2) Static mode re-transfers everything each run — usage grows with frequency even if data never changes; dynamic inverts this (deltas only). (3) Storage persists while activity resets — retention promises accumulate COGS monthly. (4) Airtable rate limits bound transfer speed — big backups cost time, not just dollars.

5 · Cost Structure

Fully serverless/usage-based stack — near-zero COGS at rest, scales with activity: Cloudflare Workers + Durable Objects, Trigger.dev v3 (per-second compute for backup tasks), DigitalOcean PostgreSQL master DB, Cloudflare D1/R2/KV/Email, Workers AI, Stripe (~2.9% + 30¢), PostHog, dub.co. The Airtable API is free — its rate limits, not dollars, are the constraint.

Fixed & step costs: base platform is low hundreds of $/mo at launch scale. Steps: dedicated DB instances (above), human support (chat / CSM / SLA where promised), SOC 2 certification, payment processing ~3% of revenue. Asymmetries to exploit: zero egress makes restore/download nearly free; dynamic incremental sync is cheaper for us and the customer at high frequency; retention is the quiet cost accumulator.

6 · Constraints & Assets

Billing infrastructure (asset)

  • Stripe: one subscription per customer org, one subscription item per platform — V2 multi-platform slots in without re-architecting.
  • Entitlements resolve from Stripe product metadata, never names — new packages are config, not code.
  • Metered billing, seat quantities, coupons, per-item trials all supported — no known blocker to tiered, usage-based, hybrid, or seat models.
  • Data model designed so plan limits live in database rows, not code — limit changes without deploys.
  • Trial mechanism live: $0 subscription at signup, no card; currently 7 days + one backup run. Trial shape (length, caps, free-tier-or-not) is open for you to revisit.

Migration constraint

~200 On2Air customers must land somewhere. Believed-real constraints: their current prices are the anchor; their product experience must not regress; legacy accounts can be flagged to see new capabilities as upgrade prompts rather than losing anything. Grandfathering duration, bridge pricing, and mapping are open — internal sketches exist if useful.

Enforcement reality (constraint)

Can gate/meter today: backup frequency, bases-per-workspace caps, trial limits, per-run record/attachment counts (recorded, not billed). Not built yet: usage metering/billing pipeline, storage quotas, seat enforcement, restore (entire feature), retention/cleanup, dynamic DB provisioning, webhooks/instant, API/SQL services, AI features. Implication: a launch model can only enforce what's built — if your recommendation depends on metering or unshipped features, please make the sequencing explicit (launch simple → layer metering, or build first).

Timeline & roadmap constraints

  • SOC 2 in progress (~6-month runway from ~Apr 2026) — enterprise/governance segment can't be broadly marketed until certified.
  • GDPR/DPAs required before hosted-data plans launch.
  • V2 roadmap must extend, not break, the model: per-platform pricing, possible multi-platform discount, AI features with real inference COGS.

Product-experience commitments (soft — challenge if warranted)

  • Restore should never feel punitive at the moment of crisis.
  • Bill-shock protection (caps, alerts, predictable defaults) is table stakes if any usage meter exists.
  • Pricing shouldn't force privacy-motivated customers into hosted storage (the BYOS "we never store your data" posture is marketed).
  • Pre-registration schema visualization stays free (conversion hook).
